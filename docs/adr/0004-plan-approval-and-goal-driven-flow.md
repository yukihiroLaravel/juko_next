# ADR-FE-0004 承認をプランの1回にし、機械の検査と観点別の評価と /goal で進める

## ステータス

承認済み (2026-11-15)

## 背景

バックエンドは ADR-0007 で、承認をプランの1回にし、`planner` エージェントがプランを作り、機械の検査と観点別の評価と /goal の判定で PR まで進める形に変えた。受講生は2つのリポジトリの両方で開発を体験するので、進め方が違うと、片方で身につけた判断の仕方がもう片方で使えない。

フロントエンドは、`change-flow` スキルで起票の前とテストを書いたあとの2か所で承認を取り、起票を `docs/changes/` に置いていた。規約は `docs/architecture/coding-standards.md`・`docs/documentation-rules.md`・`AGENTS.md`・`documentation-conventions` スキルに分かれていた。コミットの前には lefthook で整形と ESLint をかけ、型検査・テスト・本番ビルドは継続的インテグレーションでだけ見ていた。

候補は次の3つである。(a) 今の手順を保つ。(b) バックエンドの形をそのまま移す。(c) バックエンドの形を土台にし、Laravel Boost がないことと、画面を持つことに合わせて変える。

## 決定

(c) を採る。進め方、プランの形、検査を流す時機、評価の観点と回数、/goal の条件、AI がコミットと PR の作成まで行うことは、バックエンドの ADR-0007 と同じにする。そのうえで次を変える。

- 規約は `.ai/rules/` ではなく `.claude/rules/` に、パスごとに分けて置く
- コミット前のフック（lefthook）を外す
- 作業の終わりと継続的インテグレーションで流す `pnpm check-all` に、本番ビルドを含める
- 評価の前に、開発サーバーで画面を開いて確かめる段を置く。ブラウザを操作する道具がない環境では、確かめられなかったことを PR の説明に書く
- 評価の観点はバックエンドと同じ4つにし、アクセシビリティを設計と規約の観点に含める
- 画面仕様（`docs/specs/screens/`）は、触った画面の分を AI の流れの中で書く
- バックエンドの `docs/` は相対パスで参照し、worktree では git の共通ディレクトリから本体の場所を求めて探す

## 理由

- `.ai/rules/` は、バックエンドでは Laravel Boost が読ませる。フロントエンドには Boost がなく、`.ai/rules/` に置くと CLAUDE.md の指示に頼って読ませることになる。`.claude/rules/` は先頭の `paths` に当たるファイルを触ったときに Claude Code が自動で読むので、読み落としが起きにくい
- AI がコミットする流れでは、コミットの前に見るものはすべて編集の直後と作業の終わりで見終わっている。lefthook は同じ検査を3回目に流すだけになる
- 本番ビルドを含めても `pnpm check-all` は手元で30秒ほどで終わる。Server Components の境界の誤りは継続的インテグレーションで初めて分かっていたが、手元で落ちれば AI がその場で直せる
- 画面のテストは、通信と見た目を確かめない（ADR-FE-0001）。バックエンドと組み合わせたときの振る舞いは、画面を開かないと確かめられない
- アクセシビリティは独立した観点にするほど指摘が多くないと見込み、エージェントの数と受講生の利用量をバックエンドと同じにした
- 画面仕様をマージのときに人が書き起こす運用では、テストの AC-ID が仕様にないまま PR になる。AI が書けば受講生の手は増えない
- (a) は承認の関門が2つあり、手順をスキルの文章で縛るため、規約と手順の置き場が増え続けた。バックエンドと進め方が違うままになる
- (b) は `.ai/rules/` が自動で読まれず、画面の確認の段もない

## 影響

- 起動時はプランモードになり、モデルは `opusplan` を使う。サブエージェントで Opus を使うのはプランを作る `planner` だけで、評価のエージェントは Sonnet にする
- `docs/changes/` と起票の残骸を見る検査（CHK-DOC-06）を廃止した。テストの AC-ID の実在（CHK-TEST-04）は作業の終わりにだけ見る
- 以前の版で `pnpm install` をした手元には lefthook のフックが残る。消し方は README に書いた
- 継続的インテグレーションの環境にはバックエンドの `docs/` がないため、バックエンドの ID の実在は手元の作業の終わりでだけ判定される
- 画面の確認は、ブラウザを操作する道具がある環境でしか AI が行えない。ない環境では、PR を読んだ人が画面を確かめる
- 評価はトークンを使うので、受講生の利用量の上限に当たらないかを運用しながら見る
