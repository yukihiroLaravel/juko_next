# 規約の検査手段

`.claude/rules/` に定めた規約を、どこまで機械で判定できるかを整理する。区分の考え方はバックエンドの `docs/architecture/convention-checks.md` と同じである。

## 判定の区分

| 区分 | 意味                                 | 扱い                                         |
| ---- | ------------------------------------ | -------------------------------------------- |
| A    | 機械で判定でき、既存の違反が 0 件    | 直ちに検査に載せ、違反があれば落とす         |
| B    | 機械で判定できるが、既存に違反がある | 基準線を記録し、そこから増えた分だけを落とす |
| C    | 機械で検出できるが誤検知が混ざる     | 警告として出し、落とさない                   |
| D    | 機械で判定できない                   | レビューの観点として残す                     |

現時点で区分 B と C の規約はない。

## 検査手段の割り当て

| 手段                                          | 受け持つ範囲                                                           | 実行する場所                                     |
| --------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------ |
| Prettier                                      | 整形                                                                   | 編集直後・作業の終わり・継続的インテグレーション |
| ESLint（`eslint.config.mjs`）                 | import の向きなど、構文から判定できる規約                              | 編集直後・作業の終わり・継続的インテグレーション |
| `scripts/check-conventions.mjs`               | テストの書き方とドキュメント                                           | 編集直後・作業の終わり・継続的インテグレーション |
| `tsc --noEmit`                                | 型の誤り                                                               | 作業の終わり・継続的インテグレーション           |
| Vitest                                        | 画面の振る舞い                                                         | 作業の終わり・継続的インテグレーション           |
| `next build`                                  | Server Components の境界・ルーティング                                 | 作業の終わり・継続的インテグレーション           |
| 評価のエージェント（`.claude/agents/`）と人間 | 設計・責務の妥当性、セキュリティ、性能、テストの網羅、アクセシビリティ | 作業の終わりの評価・PR のレビュー                |

作業の終わり（Stop フック）と継続的インテグレーションは、同じ `pnpm check-all` を呼ぶ。判定を 2 か所に書くと、いずれ食い違う。

## 検査の実行

| 場所                                                      | 呼び方                                                        | 効き方                                                                                                                                                                                                                                            |
| --------------------------------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 編集直後（`.claude/settings.json` の PostToolUse フック） | `scripts/run node scripts/check-conventions.mjs --quiet` ほか | `.ts`・`.tsx` を書いた直後に整形・ESLint・検査スクリプトを、`.md` を書いた直後に整形と検査スクリプトを走らせ、違反があればその場で書き手に返す                                                                                                    |
| 作業の終わり（`.claude/settings.json` の Stop フック）    | `scripts/run pnpm check-all`                                  | ソース・docs・設定に変更があり、前回通ったときから作業ツリーが変わっているときだけ、すべての項目を見る。落ちたら出力を返し、1回だけ作業を続けさせる。続けたあとの終了では流さないので、直したら `scripts/run pnpm check-all` で通ることを確かめる |
| 継続的インテグレーション（`.github/workflows/ci.yml`）    | `pnpm check-all`                                              | `develop` へ向けた PR で、すべての項目を見て取り込む前に落とす                                                                                                                                                                                    |

`pnpm check-all` は、整形・ESLint・`check-conventions --merge`・型検査・全テスト・本番ビルドを順に流す。手元では30秒ほどで終わる。

コミット前のフック（lefthook）は使わない。編集直後と作業の終わりで同じものを見ており、AI がコミットする流れでは、コミットの前に見るものが残らないためである（ADR-FE-0004）。人が VS Code（Cursor など互換のエディタを含む）で書くときは、`.vscode/settings.json` が保存のたびに Prettier の整形と ESLint の自動修正をかける。

検査には見る時機が 2 つある。編集のたびに見てよいものと、作業の終わりにだけ見るものである。テストに書いた AC-ID の実在（CHK-TEST-04）は後者にあたる。テストを先に書いて AC-ID を決め、仕様への追加は実装と一緒に行うので、その間はテストの AC-ID が仕様にない。

```bash
scripts/run pnpm check-conventions        # 編集のたびに見るもの
scripts/run pnpm check-conventions-merge  # 作業の終わりにだけ見るものも含める
```

バックエンドの `docs/` の場所は `scripts/backend-docs.mjs` が求める。継続的インテグレーションの環境にはバックエンドの `docs/` がないため、バックエンドの ID の実在（CHK-TEST-04・CHK-DOC-04 の一部と CHK-DOC-05）は判定されない。これらは手元の作業の終わりの検査で見る。

検査を足したときは、違反を仕込んで実際に落ちることを確かめる。落ちることを確かめていない検査は、通っていても違反がないとは言えない。

## 対応表

既存の違反数は 2026-09-28 時点の実測である。

### 部品の構成

| ID            | 規約                                                                        | 区分 | 判定手段 | 既存の違反 |
| ------------- | --------------------------------------------------------------------------- | ---- | -------- | ---------- |
| CHK-IMPORT-01 | `features/` から `components/ui/` を直接参照しない                          | A    | ESLint   | 0 件       |
| CHK-UI-01     | Presentational でデータの取得と送信をしない（SWR・axios・ドメインのフック） | A    | ESLint   | 0 件       |
| CHK-UI-02     | Presentational に業務の判定を置かない                                       | D    | レビュー | —          |

CHK-UI-01 は型の参照を許す。Container が受け取るコールバックの型をフックの側で定義している箇所があるためである。

CHK-IMPORT-02 は、共通へ移すべきかの判断を伴うため機械では落とさない。

### テスト

| ID          | 規約                                    | 区分 | 判定手段                                                     | 既存の違反 |
| ----------- | --------------------------------------- | ---- | ------------------------------------------------------------ | ---------- |
| CHK-TEST-02 | `Arrange`・`Act`・`Assert` を書く       | A    | 検査スクリプト                                               | 0 件       |
| CHK-TEST-03 | `describe` と `it` の名前を日本語で書く | A    | 検査スクリプト                                               | 0 件       |
| CHK-TEST-04 | 参照する受け入れ基準が実在する          | A    | 検査スクリプト（作業の終わりと継続的インテグレーションのみ） | 0 件       |
| CHK-TEST-05 | 見た目や通信を確かめていない            | D    | レビュー                                                     | —          |
| CHK-TEST-06 | 要素を利用者に見えるもので探す          | D    | レビュー                                                     | —          |

CHK-TEST-01 は欠番である。バックエンドの番号と揃えるため空けている（置き場の判定は区分 C 相当で、載せる価値が小さい）。

CHK-TEST-03 は日本語であるかまでしか判定できない。利用者の視点になっているかはレビューで見る。

CHK-TEST-04 は、バックエンドの機能の略称を持つ ID（`AC-ENROLL-NNN` など）を、バックエンドの `docs/` が見つかるときだけ判定する。

| CHK-DOC-05 | `TODO(Q-NNN)` の記録が実在する | A    | 検査スクリプト | 0 件       |
| CHK-DOC-07 | 太字記法と区切り線を使わない   | A    | 検査スクリプト | 0 件       |

CHK-DOC-04 と CHK-DOC-07 は、雛形とこの文書が仮の ID や禁止した書き方を例として含むため、`template.md` で終わるファイルとこの文書を対象から外す。

CHK-DOC-01 から CHK-DOC-03 と CHK-DOC-09 は、業務知識の文書に対する検査であり、業務知識を持たないこのリポジトリでは使わない。番号はバックエンドと揃えるため空けている。

CHK-DOC-06 は、実装が終わった起票を `docs/changes/` に残さない規約だった。プランを `.claude/plans/` に置いて git の管理から外したため、規約ごと廃止した（ADR-FE-0004）。番号は空けたままにする。

## レビューの重大度

評価のエージェントと PR のレビューでは、指摘ごとに重大度を付ける。

| 重大度   | 対象                                                                                                                                                                                       |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `must`   | セキュリティ・データの取り違え・規約の必須違反（Presentational での取得と送信、`components/ui/` の直接参照、送信の失敗を利用者に伝えない）。プランで承認した「確かめること」にテストがない |
| `should` | 設計規約からの逸脱、テスト不足（置き場と命名の違反、振る舞いの変更にテストがない、読み込み中・失敗・0件の表示の欠落）、キーボードで操作できない・ラベルのない入力                          |
| `nits`   | 軽微な指摘や好みの範囲                                                                                                                                                                     |

次は機械で判定できないため、レビューの観点として残す。評価のエージェント（`.claude/agents/`）と、PR をレビューする人がこの一覧を見る。

| ID            | 観点                                               | 重大度 |
| ------------- | -------------------------------------------------- | ------ |
| CHK-DATA-01   | 送信の失敗を利用者に伝えているか                   | must   |
| CHK-UI-02     | Presentational に業務の判定が入っていないか        | should |
| CHK-IMPORT-02 | ドメインをまたいだ参照                             | should |
| CHK-DATA-02   | 3つの状態の表示の欠落                              | should |
| CHK-DATA-03   | 部品の中で `isLoading`・`error` を分岐していないか | should |
| CHK-TEST-05   | 見た目や通信のテストになっていないか               | should |
| CHK-TEST-06   | クラス名や `data-testid` で探していないか          | nits   |
