# コーディング規約

このプロジェクト固有の実装ルールを定める。React と Next.js の汎用的なベストプラクティスは `nextjs-best-practices` スキルを参照し、汎用ルールと衝突する場合はこちらを優先する。

既存コードには本規約が策定される前の書き方が残っている。新規実装と修正のときに本規約を適用し、既存コードの一括での作り替えは行わない。

## 現行コードとの差異

| 項目                   | 規約                                                         | 既存コード                                                                                                                                                                                                                                                               |
| ---------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 読み込み中と取得の失敗 | Suspense と ErrorBoundary に統一する（下の「非同期の状態」） | 講座詳細・レッスンの部品（チャプター一覧・レッスン・各サイドバー・進捗のまとめ・パンくず）が `isLoading` と `error` で分岐している。その部品を修正するときに移す。認証まわり（認証の確認・ヘッダー）も分岐しているが、下の「例外」の候補であり、扱いが決まるまで移さない |
| テスト                 | 振る舞いを変えたらテストを書く                               | 規約の策定前に書かれた部品にはテストがない                                                                                                                                                                                                                               |

## Container と Presentational

部品は原則として Container と Presentational に分ける。

| ファイル              | 役割             | 持ってよいもの                                                              |
| --------------------- | ---------------- | --------------------------------------------------------------------------- |
| `<部品>.tsx`          | Container        | 状態・データの取得と送信・変換・イベントの処理                              |
| `<部品>.ui.tsx`       | Presentational   | props で受けた値の表示・UI の一時的な状態（開閉・パスワードの表示切替など） |
| `<部品>.skeleton.tsx` | 読み込み中の表示 | 表示だけ                                                                    |
| `<部品>.test.tsx`     | テスト           | —                                                                           |

- Presentational はデータの取得と送信をしない。SWR・axios・ドメインのフックを呼ばない。型の参照はしてよい
- Presentational は業務の状態を持たない。業務の判定（期限切れか、完了できるか）は Container で行い、真偽値や文言で渡す
- ページ（`app/` の `page.tsx`）は Container を並べ、Suspense と ErrorBoundary で囲むだけにする。業務の処理を書かない

## 置き場

横断的に使うものは `src/` 直下、ドメイン固有のものは `src/features/<ドメイン>/` に置く。

```
src/features/<ドメイン>/
  components/<部品>/   部品ごとに1ディレクトリ
  hooks/               use<処理>.ts
  types/               API の応答の型
  utils/               map<元>To<先>.ts・swrKeys.ts
  validation/          <フォーム>Schema.ts
```

- ドメインをまたいで使うようになったら、`src/` 直下の共通ディレクトリへ移す。別のドメインの `features/` を参照しない
- 画面のパスは `src/lib/routes.ts` の `routes` から取る。文字列で組み立てない

## 共通部品の腐敗防止層

shadcn/ui の部品は `components/ui/` に生成されるが、`features/` から直接参照しない。`components/atoms/` で再公開したものを使う。

```
src/components/
  ui/button.tsx       shadcn/ui の生成物（直接参照しない）
  atoms/Button.tsx    ui/button を再公開する
```

shadcn/ui の部品を足したときは、同じ変更で `atoms/` に再公開のファイルを足す。

## データの取得と送信

- 取得は SWR のフックに包み、`features/<ドメイン>/hooks/use<対象>.ts` に置く。SWR は `suspense: true` で呼び、フックは画面で使う形の値（`attendanceDetail`）だけを返す。`isLoading` と `error` は返さない（下の「非同期の状態」）
- SWR のキーは `utils/swrKeys.ts` に関数で置く。取得と再検証で同じキーを使うためである
- 送信は `use<処理>.ts` のフックに包み、`{ success: true }` か `{ success: false, error: <利用者向けの文言> }` を返す。例外を Container へ投げない
- 送信が成功したら、影響する取得のキーを `mutate` で再検証する
- 利用者向けのエラーの文言はフックで決める。Container と Presentational で HTTP の状態コードを見ない
- 応答の型は `types/` に置き、画面の形への変換は `utils/map<元>To<先>.ts` に置く。Presentational に応答の型をそのまま渡さない

## 非同期の状態

Async React の考え方を採る（ADR-FE-0002）。待つこと・失敗すること・前の表示を残すことを、部品の中の分岐ではなく React の仕組みに任せる。

| 状態             | 受け持つもの                                                      |
| ---------------- | ----------------------------------------------------------------- |
| 読み込み中       | Suspense の代替表示（`<部品>.skeleton.tsx`）                      |
| 取得の失敗       | ErrorBoundary の代替表示                                          |
| 取り直している間 | transition（`useTransition`・`useDeferredValue`）で前の表示を残す |
| 0件              | Container。空であることを Presentational へ渡して表示する         |

読み込み中・取得の失敗・0件の3つは、どの画面でも必ず表示を決める。

### 取得

- 取得のフックは SWR を `suspense: true` で呼ぶ。Container で `isLoading`・`error` による分岐を書かない
- Suspense と ErrorBoundary は、ページか、失敗しても残りの画面が使える区画の単位で置く。ErrorBoundary を Suspense の外側にする
- ErrorBoundary の代替表示には、何が失敗したかと再試行の手段を置く
- 検索の条件やタブを変えて取り直すときは、条件の更新を `startTransition` で包むか、条件を `useDeferredValue` で遅らせる。代替表示へ戻さず前の結果を残し、取り直していることは `isPending` で示す

### 送信

- 送信の失敗は ErrorBoundary に投げない。送信のフックが結果を値で返し、操作した場所の近くに出す（上の「データの取得と送信」）
- 新しく書く送信は、送信中の状態を `useState` で持たず、`useTransition` の `isPending`（React の Actions）で表す。フォームは `useActionState` を使ってよい
- 成功を待たずに表示を変えたいときは `useOptimistic` を使う。失敗したときは React が元の表示に戻す

既存の送信のフックは送信中の状態を `useState` で持っている。そのフックを修正するときに移す。

### 例外

Suspense が合わない使い方もありうる。そう見えたときは、自分で判断して `isLoading` の分岐で書かず、関門1で依頼者に確認する。扱いが決まったらこの節に書き足す。

検討が要りそうな場面の例は次のとおりである。

- ログイン中の利用者の取得。未ログインなら別の画面へ移す判定を伴い、今は認証の確認とヘッダーが `isLoading` で分岐している
- 取得するかどうかが操作によって決まり、キーが `null` になる間の表示
- 画面の一部だけを、画面の他の部分より後から表示したいとき

## フォーム

- React Hook Form と zod で書く。スキーマは `validation/<フォーム>Schema.ts` に置く。そのフォームでしか使わない小さなスキーマは Container に置いてよい
- 送信の失敗でサーバーから返った文言は `form.setError` で該当の項目に出す
- 送信中は送信のボタンを押せなくする

## 表示の文言

- 用語はバックエンドの `docs/domain/shared/glossary.md` に従う。画面の文言でも講座をコースと書かない
- 利用者向けの文言は日本語で書く

## TypeScript

- `any` を使わない。応答の型が分からないときは `unknown` で受けて絞り込む
- React Compiler が有効である。値の再計算を避けるためだけの `useMemo`・`useCallback` を新たに書かない

## コード品質

- 整形は Prettier、検査は ESLint と `scripts/check-conventions.mjs` で行う
- 規約の検査手段は `convention-checks.md` にある

実行するコマンドは `AGENTS.md` にある。

## 実装の進め方

実装は TDD で進める。失敗するテストを先に書き、それを通す形で実装する。

| 段       | 内容                                                               |
| -------- | ------------------------------------------------------------------ |
| 起票     | 変更の範囲を決める。書く前に依頼者の承認を取る                     |
| Red      | 失敗するテストを書く。書いたあと、実装に入る前に依頼者の承認を取る |
| Green    | テストを通す最小の実装を書く                                       |
| Refactor | 規約に合わせて整える                                               |
| 評価     | 検査・型検査・全テストを通し、画面を実際に開いて確かめる           |

承認を取る場所が2つあるのは、取り違えを直す費用が段を追うごとに上がるためである。Red の段が仕様の確定点になる。

検査と型検査は規約に合っているかだけを見ており、振る舞いが正しいかは見ていない。両者を混同しない。

## テスト

テストは画面の単位で、利用者の操作と状態に応じた振る舞いを確かめる（ADR-FE-0001）。

### 確かめること

| 種類               | 例                                                    |
| ------------------ | ----------------------------------------------------- |
| 操作の結果         | ログインに失敗したとき、失敗の理由が表示される        |
| 状態による出し分け | 期限切れの受講では、完了のボタンが出ない              |
| 入力の検証         | パスワードが8文字に満たないとき、送信せずに入力を促す |
| 送信中の扱い       | 送信中は、もう一度送信できない                        |

境界の値を必ず1つは入れる。ちょうど8文字、ちょうど期限日のような、間違いが出やすい点である。

### 確かめないこと

| 種類                                                | 理由                                                             |
| --------------------------------------------------- | ---------------------------------------------------------------- |
| API と通信しているか・送る値の形                    | バックエンドのテストが受け持つ。フックを差し替えて通信を切り離す |
| 見た目（部品の並び・余白・色・クラス名）            | デザインの担当である。表示の調整のたびに落ちる                   |
| 部品が描画されること自体                            | 振る舞いを確かめていない                                         |
| ライブラリの動作（zod や React Hook Form そのもの） | ライブラリの責任である                                           |

「検索ボックスの隣に検索のボタンがある」は見た目であり、書かない。「検索のボタンを押すと、条件に合う講座だけが並ぶ」は振る舞いであり、書く。

### 書き方

- Container を描画する。Presentational だけを描画して props の表示を確かめるテストは書かない
- データのフックは `vi.mock` で差し替え、`vi.mocked(useXxx).mockReturnValue(...)` で状態を与える。HTTP の層を差し替えない
- 要素は利用者に見えるもので探す。`getByRole`・`getByLabelText`・`getByText` を使い、クラス名や `data-testid` で探さない
- 操作は `@testing-library/user-event` で行う
- 読み込み中と取得の失敗は Suspense と ErrorBoundary が受け持つため、それを置いた単位で描画して確かめる。取得の失敗は、差し替えたフックに例外を投げさせて再現する
- 対象の Container と同じディレクトリに `<部品>.test.tsx` で置く
- `describe` は画面や部品の呼び名、`it` は何をしたら何が起きるかを、どちらも日本語で書く。部品名や変数名をそのまま使わない
- AAA パターンを利用し、必ずコメントで `Arrange`・`Act`・`Assert` を記述する
- 対応する受け入れ基準があるときは、`it` の直前に AC-ID をコメントで書く

```tsx
// AC-LESSON-003
it('レッスンを完了にすると、完了済みの印が付く', async () => {
  // Arrange
  // Act
  // Assert
});
```

見本は `src/features/auth/components/LoginForm/LoginForm.test.tsx` にある。

## レビュー時の重大度

| 重大度   | 対象                                                                                                                                       |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `must`   | セキュリティ・データの取り違え・規約の必須違反（Presentational での取得と送信、`components/ui/` の直接参照、送信の失敗を利用者に伝えない） |
| `should` | 設計規約からの逸脱、テスト不足（置き場と命名の違反、振る舞いの変更にテストがない、読み込み中・失敗・0件の表示の欠落）                      |
| `nits`   | 軽微な指摘や好みの範囲                                                                                                                     |
