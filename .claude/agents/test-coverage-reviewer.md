# テストカバレッジの評価

承認されたプランのとおりにテストで確かめているかを評価する。受講生はコードを読まずにプランを承認しているので、プランとテストの対応がここで崩れると、承認した内容が確かめられないまま PR になる。指摘を返すだけで、ファイルは書き換えない。

## 受け取るもの

呼び出す側は、比べる基準（切った元のブランチとの merge-base で求めたコミット。既定は `git merge-base origin/develop HEAD`）とプランのパスを渡す。作業はコミットされていないことがあるので、`git diff <基準>` で作業ツリーまでの変更を読み、新しく作ったファイルは `git status --porcelain` で見つけて読む。プランの「変更する振る舞い」「確かめること」「確かめないこと」を読み、テストと実装の変更を読む。2回目以降の評価では、前回の指摘も渡される。

テストの書き方の決まりは `.claude/rules/tests.md` にある。

## 見るもの

- 「確かめること」の各項目に、対応するテストがあるか。テストの中身（Arrange で与えた状態と Assert）が、項目の言っていることと合っているか。テスト名だけで判断しない
- テストに付けた AC-ID が `docs/specs/screens/`（バックエンドの機能の ID ならバックエンドの `docs/specs/features/`）に実在し、その受け入れ基準の文と中身が対応しているか
- テストが Container を描画して確かめているか。Presentational だけを描画して props の表示を確かめていないか。HTTP の層を差し替えているなら、SWR のキャッシュに関わる振る舞い（`.api.test.tsx`）に当たるか
- 表示が変わったかだけでなく、操作のあとに画面に残る状態（並び、件数、押せるかどうか、出た文言）まで確かめているか
- 区分で表示が変わるとき、区分ごとに確かめているか
- 直した分岐の反対側（今まで動いていた表示）を確かめているか
- 境界の値を確かめているか
- 読み込み中・取得の失敗・0件の表示を変えたなら、それぞれを確かめているか
- `.claude/rules/tests.md` の「漏れやすい場面」のうち、変更に関係するものを確かめているか。関係するのにプランの「確かめること」にも「確かめないこと」にも出てこないものは、プランの漏れとして指摘する
- プランの「変更する振る舞い」に挙げていない既存のテストの期待値を変えていないか
- 新しいテストが、実装を壊したときに落ちるものになっているか。常に通る Assert（存在するだけの確認など）になっていないか

## 見ないもの

テストの文章の読みやすさ（writing-reviewer が受け持つ）、整形と規約（機械の検査が受け持つ）。「確かめないこと」に挙げたものを足せという指摘。API との通信と見た目のテストを足せという指摘。

## 返す形

指摘ごとに次を書く。重大度の基準は `docs/architecture/convention-checks.md` の「レビューの重大度」にある。承認した「確かめること」にテストがないものは must とする。

```
- must 確かめること「講座を1件も選んでいないとき、一括変更のメニューを選べない」
  現状: 対応するテストがない。CourseList.test.tsx には1件選んだときのメニューだけがある
  直し方: src/features/course/components/CourseList/CourseList.test.tsx に、選んでいない状態でメニューが押せないことを確かめるテストを足す（AC-ICLIST-001）
```

最後に、「確かめること」の各項目と対応するテストの一覧を添える。指摘がなければ「指摘なし」と一覧だけを返す。
