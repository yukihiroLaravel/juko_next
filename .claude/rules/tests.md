# テスト

テスト戦略の原則は `CLAUDE.md` の「テストの方針」にある。ここでは書き方を定める。汎用的な書き方は `nextjs-best-practices` スキルの `rules/testing.md` にある。

## 確かめること

テストは画面の単位で、利用者の操作と状態に応じた振る舞いを確かめる（ADR-FE-0001）。

| 種類               | 例                                                    |
| ------------------ | ----------------------------------------------------- |
| 操作の結果         | ログインに失敗したとき、失敗の理由が表示される        |
| 状態による出し分け | 期限切れの受講では、完了のボタンが出ない              |
| 入力の検証         | パスワードが8文字に満たないとき、送信せずに入力を促す |
| 送信中の扱い       | 送信中は、もう一度送信できない                        |

## 確かめないこと

| 種類                                                | 理由                                                             |
| --------------------------------------------------- | ---------------------------------------------------------------- |
| API と通信しているか・送る値の形                    | バックエンドのテストが受け持つ。フックを差し替えて通信を切り離す |
| 見た目（部品の並び・余白・色・クラス名）            | デザインの担当である。表示の調整のたびに落ちる                   |
| 部品が描画されること自体                            | 振る舞いを確かめていない                                         |
| ライブラリの動作（zod や React Hook Form そのもの） | ライブラリの責任である                                           |

「検索ボックスの隣に検索のボタンがある」は見た目であり、書かない。「検索のボタンを押すと、条件に合う講座だけが並ぶ」は振る舞いであり、書く（CHK-TEST-05）。

## 書き方

- Container を描画する。Presentational だけを描画して props の表示を確かめるテストは書かない
- データのフックは `vi.mock` で差し替え、`vi.mocked(useXxx).mockReturnValue(...)` で状態を与える。HTTP の層を差し替えない。例外は下の「SWR のキャッシュに関わる振る舞い」だけである
- 要素は利用者に見えるもので探す。`getByRole`・`getByLabelText`・`getByText` を使い、クラス名や `data-testid` で探さない（CHK-TEST-06）
- 操作は `@testing-library/user-event` で行う
- 読み込み中と取得の失敗は Suspense と ErrorBoundary が受け持つため、それを置いた単位で描画して確かめる。取得の失敗は、差し替えたフックに例外を投げさせて再現する
- 対象の Container と同じディレクトリに `<部品>.test.tsx` で置く
- `describe` は画面や部品の呼び名、`it` は何をしたら何が起きるかを、どちらも日本語で書く。部品名や変数名をそのまま使わない（CHK-TEST-03）
- AAA パターンで書き、コメントで `Arrange`・`Act`・`Assert` を必ず書く（CHK-TEST-02）
- 対応する受け入れ基準があるときは、`it` の直前に AC-ID をコメントで書く。仕様を変えたときに `grep -rn 'AC-ICLIST-001'` で仕様とテストを同時に引けるようにするためである。書いた AC-ID が `docs/specs/` かバックエンドの `docs/` に実在するかは、作業の終わりに CHK-TEST-04 で検査する

```tsx
// AC-ICLIST-001
it('講座を1件も選んでいないとき、一括変更のメニューを選べない', async () => {
  // Arrange
  // Act
  // Assert
});
```

見本は `src/features/auth/components/LoginForm/LoginForm.test.tsx` にある。

## 落ちることを確かめる

テストは、確かめたい誤りがあるときに落ちることを確かめてから信じる。

- 新しい振る舞いのテストは、実装の前に書いて落ちることを確かめる
- まだ存在しない部品やフックを対象にするときは、Container とフックの空の骨組み（何も表示しない・何もしない）だけを先に作ってよい。import の失敗で落ちると、振る舞いがないから落ちているのかを確かめられないためである
- 今の振る舞いを守るテスト（直す分岐の反対側など）は最初から通る。実装を一時的に壊して落ちることを確かめ、元に戻す
- 落ちることを確かめていないテストは、通っていても何かを確かめているとは言えない

## 確かめる中身

- 表示が変わったかだけでなく、操作したあとに画面に残る状態（並び、件数、押せるかどうか）まで確かめる
- 区分（受講生・講師・マネージャー）で出し分ける表示は、区分ごとに確かめる
- 直す分岐の反対側、つまり今まで動いていた表示も確かめる
- 境界の値（ちょうど8文字、受講期限の当日と翌日など）を必ず1つは入れる

## 漏れやすい場面

変更に関係するものは、確かめるかを検討する。プランを作るときと、テストカバレッジを評価するときもこの一覧を使う。

- 0件のとき、読み込み中、取得の失敗。0件の表示を決め忘れやすい
- 送信が失敗したときの文言の出し分けと、送信中にもう一度押したとき
- 区分で出し分ける表示とメニュー
- 日時や値が空のとき（一度もログインしていない受講生、期限なしの受講など）
- 受講期限の当日と翌日（BR-SHARED-006）
- 検索の条件やタブを変えて取り直すとき、前の結果を残して取り直していること

## SWR のキャッシュに関わる振る舞い

開き直したときに取り直すか、取得できた値を残すか、送信の成功後に一覧を取り直すかは、フックを差し替えると SWR が動かず確かめられない。これに限り、`@/lib/api` の axios を差し替えて本物の SWR を動かす（ADR-FE-0003）。

- `<部品>.api.test.tsx` として、対象の Container と同じディレクトリに置く
- `SWRConfig` の `provider` でテストごとに新しいキャッシュを渡す
- 確かめるのは取得と再取得の有無と、画面に出る結果である。送る値の形や API のパスは確かめない
- フックのテストを別に書かない。上と同じく Container を描画する

## 既存のテストを変えるとき

プランの「変更する振る舞い」に挙げたもの以外のテストが落ちたら、テストを直さずに実装を疑う。期待値を変えたときは、どのテストをなぜ変えたかを PR の説明に書く。

規約を決める前に書かれた部品にはテストがない。その部品の振る舞いを変えるときにテストを足す。
