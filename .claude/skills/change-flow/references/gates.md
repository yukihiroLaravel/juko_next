# 関門で提示する形

2つの関門はどちらも AskUserQuestion で聞く。依頼者には開発の経験が浅い者が多い前提で書く。

共通の原則は3つである。

- 利用者の言葉で書く。部品名・フック名・ファイルパス・props の名前を出さない
- 判断に必要なものだけを出す。全文を読ませない
- 選択肢に「承認」以外の出口を必ず用意する。承認しか押せない関門は関門ではない

## 関門1 起票の承認

起票のファイルを作る前に聞く。

### 質問文に載せる内容

```
この変更で行うことを整理しました。これで進めてよいですか。

変更する振る舞い
  ・レッスンの画面に「完了にする」ボタンを置き、押すと完了済みの印が付く
  ・受講期限を過ぎた受講では、ボタンを出さない
    （画面が前提にする API の振る舞い AC-PROG-004）

変更する範囲
  ・レッスンの画面の表示
  ・レッスンを完了にする操作
  ・完了したあとの講座の進捗の表示の更新

対象外
  ・完了を取り消す操作
  ・講座一覧の画面の進捗の表示
```

### 必要な API がまだないとき

3点の前に次を足す。選択肢には「API ができるまで待つ」を足す。

```
この画面が使う「レッスンを完了にする」API は、まだバックエンドにありません。
画面だけを先に作り、API がない間は操作できない状態にしておくこともできます。
```

### 未確定事項と矛盾するとき

依頼がバックエンドの `docs/domain/open-questions.md` の暫定方針を覆す方向のときは、この関門で一緒に確認する。書き方はバックエンドの `change-flow` の `references/gates.md` と同じである。選択肢には「暫定方針のままにする」を足す。

### 選択肢

| 選択肢                     | 意味                   | 次にすること           |
| -------------------------- | ---------------------- | ---------------------- |
| この内容で進める           | 承認                   | 起票を書いて段2へ      |
| 変更する振る舞いが違う     | 何を作るかの取り違え   | 段0へ戻って聞き直す    |
| 範囲が広すぎる、狭すぎる   | どこまでやるかの認識差 | 範囲を詰め直す         |
| 対象外に入れたいものがある | やらないことの追加     | 対象外を足して聞き直す |

## 関門2 テストの承認

失敗するテストを書いたあと、実装に入る前に聞く。

ここが仕様の確定点である。承認されたものを実装するので、ここで見落とした観点は実装にも入らない。

### 見せないもの

- テストのコード
- 部品名・フック名・ファイルのパス
- モックや照合の話

### 質問文に載せる内容

テストの名前は日本語で利用者の視点で書く決まりになっている。ほぼそのまま箇条書きに写せる。

```
実装の前に、画面で何を確かめるかを決めました。これで合っていますか。

確かめること

  ・「完了にする」を押すと、そのレッスンに完了済みの印が付く
  ・完了に失敗したとき、失敗の理由が表示され、印は付かない
  ・完了の処理中は、もう一度押せない
  ・受講期限の当日は、まだボタンが出る
  ・受講期限を過ぎた受講では、ボタンが出ない

確かめないこと

  ・完了の API が正しく呼ばれているか（バックエンドで確かめている）
  ・ボタンの位置や色
  ・講座一覧の画面の進捗が変わるか
```

境界の値を必ず1つは入れる。「期限の当日」「ちょうど8文字」のような、間違いが出やすい点である。

「確かめないこと」を書くのは、依頼者が「それも見てほしい」と言える余地を作るためである。通信と見た目は既定で確かめないことを、毎回ここに書いて示す。

### 選択肢

| 選択肢                   | 意味             | 次にすること            |
| ------------------------ | ---------------- | ----------------------- |
| この内容で実装に進む     | 承認             | 段5へ                   |
| 確かめる観点が足りない   | 抜けの指摘       | 段3へ戻ってテストを足す |
| 確かめることが期待と違う | 仕様の取り違え   | 段3へ戻って書き直す     |
| 対象の前提が違う         | もっと手前の誤り | 段0へ戻る               |

## 迷ったとき

関門を通すかどうかで迷うくらいなら通す。実装が終わってから取り違えが分かると、捨てる量が桁違いになる。

逆に、関門を増やしすぎない。関門はこの2つだけにする。API の有無や未確定事項との矛盾は、3つ目の関門を立てるのではなく関門1の提示に含める。
